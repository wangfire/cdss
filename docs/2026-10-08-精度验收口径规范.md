## 1. 为什么要这份规范

同一个系统在两份报告里给出了互相打脸的精度数字：

| 来源 | 样本 | 编码级 Top1 | 类目级 Top1 | 出码率 |
|---|---|---|---|---|
| `evaluate-accuracy`（90 例精标语料，`docs/superpowers/reports/accuracy-baseline-20261007-05-final.json`） | 83 例可评 | **63.9%** | **83.1%** | 89.2% |
| 1000 病案 / 10000 诊断名管道台账（`data/exports/2026-09-30-1815-…构词性后缀版.xlsx`） | 10000 名 | **13.7%** | **25.8%** | 67.1% |

决策 3 的验收线写的是"编码级 Top1 ≥25%、类目级 Top1 ≥50%，以**万条回归自动口径** + 人工抽查 50 例校准后的口径为准"。按万条数字两项都不达标，按 90 例数字两项都远超——**"达没达标"这个问题目前无法回答**，这就是本规范要消除的歧义。

根因不在算法，而在**分母**：万条单名语料里混着三类性质完全不同的事——

1. 院内编码依据的是**医疗过程事实**（做过手术、在化疗、带装置），诊断名文本里没有这个事实；
2. 索引词表**根本没有这个词**（心功能、早搏、肛裂、包皮），属知识库缺口；
3. 词表有锚点、链路也跑通了，**算法选错了码**——这才是匹配算法该被考核的部分。

把这三类混在一个分母里，既低估了算法、也掩盖了知识库治理的欠账。本规范把它们拆成可分别问责的层，并**冻结判据**，防止"换口径刷分"。

## 2. 判定基础（命中、类目、归一、去重）

| 项 | 规定 | 说明 |
|---|---|---|
| 语料 | 本机 JZEY 单诊断名测试集：医院 `868F2319-9A0C-46C8-B478-C78FB350237D`，`patient.display_name LIKE 'JZEY测试-%'`，`coding_diagnosis_input.source_type='FRONT_PAGE'` | 换语料用 `--hospital` / `--patient-prefix` 覆盖，判据不变 |
| 对照码 | 同实例上的源库 `WaterCloudNetDb_JZEY.dbo.DiagnosticSet_LCZD`（`Name`→`Code`，119115 个名） | 命令分两次查询、在内存按名对齐，避免跨库字符串比较触发排序规则冲突 |
| 归一 | 去所有空白、大小写不敏感、联合码 `†` 归一为 `+` | 与 `evaluate-accuracy` 一致；此前导出链踩过的"联合码被空格截断产生假差异"在本命令里由归一规则从根上堵住 |
| 编码级命中 | 推荐码归一后与对照码集合**相等** | 同名多条对照码时按"任一命中"（见 §3 E4） |
| 类目级命中 | 编码**前 3 位**相等（`E11`/`I25`/`K29`…） | 手术码（ICD-9-CM-3）为数字段，同规则不适用，本口径只测诊断通道 |
| 名去重 | 按 `original_text` 精确分组，`ROW_NUMBER() OVER (PARTITION BY original_text ORDER BY created_at, id) = 1` | 1000 任务下 11419 条 FRONT_PAGE 输入 → 10000 个名，与交付工作簿一致 |
| Top-k | 同一名的 ACTIVE 推荐按 `rank` 升序取前 3 | 只统计 `lifecycle_status='ACTIVE'`，已确认结果保护产生的重复推荐不参与 |
| 通道 | 本轮 100% 为 ICD_INDEX 通道 | 向量/Rerank 通道在 L3 语料上参与，L0/L1 无贡献 |

## 3. 剔除判据 E1–E5（已冻结）

| 判据 | 定义 | 领域依据（为什么"不该由诊断名推出"） | 本轮数量 | 样例（诊断名→院内码） |
|---|---|---|---|---|
| **E1 状态与医疗接触码** | 对照码章节 = `Z` | ICD-10 Z 章定义是"影响健康状况的危险因素和保健接触"，编码依据是**治疗/手术/随访等过程事实**，单名文本不含该事实 | **1851**（占 18.5%） | 甲状腺切除术后→Z98.800；食管癌术后→Z51.102；恶性肿瘤靶向治疗→Z51.801；心功能Ⅲ级→Z95.501 |
| **E2 外部原因码** | 对照码章节 ∈ `V/W/X/Y` | 这四章编码"损伤的外部原因/运输事故/意图不确定事件"，是独立于疾病诊断的第二部分编码任务；且本地 ICD 索引主导词表未收录外部原因词汇 | **30** | 被别人殴打、踢、拧、咬或抓伤→W50.X00；行人在交通事故中的损伤→V09.300 |
| **E3 索引无锚点** | `IcdIndexDiag --blank` 复算判定 = **无主导词召回** | 主导词在索引词表里**一个都没召回**，链路根本没开始走，属知识库覆盖治理（B3-5/B4-2），不是排序或门控问题 | **1603**（占 16.0%）；**其中 0 名有推荐** | 心功能Ⅰ级→I50.902；陈旧性前壁下后壁→I25.200；肛裂→K60.200；包皮过长→N47.X01 |
| **E4 对照码自相矛盾** | 同一 `Name` 在源字典里有 ≥2 个不同 `Code` | 对照本身不可信，命中与否取决于取哪一条，属源数据缺陷；L0 按"任一命中"计，L1 整条剔除 | **244**（清单里 E4 标签 139，其余被 E1/E2/E3 先命中） | 窦性心动过缓→`R00.100/R00.100X001/R16.100X001`；2型糖尿病酮症酸中毒→`E11.101/E11.700` |
| **E5 对照码缺失** | 名字在源字典查不到编码 | 无法判定，只能剔除 | **0** | — |

**判据侧的三条硬约束：**

1. **E3 不许用来掩盖召回缺陷。** E3 只覆盖"无推荐"的名（本轮 1603 名 0 有推荐），所以它**不改变任何命中数，只改变分母**。发布时必须同时披露 E3 里对照码落在实体疾病章的部分——本轮 1603 名里 **1216 名不是 Z 章**（O 291、S 220、C 112、R 112、I 110、K 72…），这 1216 名是知识库**必须补词**的工作项，不是可以一剔了之的噪声。
2. **E4 只影响 L0 的命中判定，不影响 L1。** 一旦改成"矛盾名也算命中/也算未命中"都会让两层不可比。
3. **判据先于结果固定。** 本表 E1/E2 的章节划分来自 ICD-10 章节定义本身，不是从命中分布里挑出来的（见 §6 第 5 条的变更流程）。

### 4.3 L1 剩余未命中的构成（这才是算法欠账）

L1 的 6760 名里 Top1 未命中 **5409 名**：**有推荐但错码 4184 名（61.9%）**、无推荐 1225 名（18.1%）。按对照章分布：

`I 791 ｜ S 610 ｜ C 598 ｜ R 568 ｜ D 421 ｜ K 352 ｜ M 337 ｜ N 324 ｜ T 307 ｜ E 195 ｜ J 191 ｜ O 171 …`

四个可执行的补齐方向已经写死在这里（均属阶段计划 WP-B4-2 范围）：

- **C 章 598 名**：肿瘤的"另见"按部位改道 + M 形态码引导编码尚未实现；
- **S 章 610 名**：部位/侧别扩展码不来自索引链路（已知口径，如 胫前动脉 I74.300X232），需要扩展码表或部位词到扩展码的映射；
- **R 章 568 名**：症状体征名按病变名索引（"待查/原因不明"类），需要症状通道；
- **I 章 791 名**：内科最大章，含大量真实排序缺陷，是门控/排序调优的主战场。

## 5. 复算方法

```bash
# 1) 前置：管道落库（rerun_batch.js 1000 3）后，取无推荐名单跑离线归因
dotnet run --project tools/IcdIndexDiag --no-build -- --blank <noRecNames.txt> <norec_stage.tsv>

# 2) 分层口径复算（对照码与推荐台账都从库里读）
dotnet run --project tools/HospitalAi.Tools --no-build --no-restore -- caliber \
  --connection "<HospitalAi 连接串>" \
  --hospital 868F2319-9A0C-46C8-B478-C78FB350237D \
  --patient-prefix "JZEY测试-" \
  --attribution <norec_stage.tsv> \
  --report  docs/superpowers/reports/accuracy-caliber-<日期-时分>.json \
  --excluded <剔除清单.tsv> \
  --dump     <逐名台账.tsv>
```

产物：`accuracy-caliber-*.json`（分层数字 + 剔除计数 + L2 指标，随仓库归档）、`--excluded` 逐名剔除清单（判据可人工复核）、`--dump` 逐名台账（对照码全集、Top1 码、Top1 是否索引码回退、三项命中标志、剔除判据）。

**与交付工作簿的对账：** L0 编码级 Top1 为 **1395**，交付的 9-30 工作簿口径为 **1374**，差 **21 名**。逐名核验后 21 名**全部**落在 E4（同名多条对照码）上，且方向单一——工作簿按种子映射只取一条码，本命令按"任一对照码命中"，**0 名反向丢分**。这 21 名在 L1 里已整条剔除，因此 **L1 的数字不受该规则影响**。

## 6. 治理规则

1. **L0 永远并列发布。** 任何对外报告只给 L1 或只给 L3，都视为口径违规。
2. **判据变更走版本。** §3 表一经发布即冻结；新增剔除类别必须（a）给出 ICD-10 章节/索引约定层面的定义依据，（b）用**历史已交付轮次**重算并公布前后差值，（c）在本文档追加判据版本号。
3. **敏感度表必发。** §4.2 的逐条剔除步骤与 L1 未命中章分布（§4.3）必须与主表同发，让"L1 涨了多少、涨在哪"可被反驳。
4. **剔除清单可复核。** 每次发布都要带 `--excluded` 的逐名清单，任何人都能抽查"这名凭什么剔"。
5. **不许用剔除达标。** 若某一层剔除后仍不达线，结论必须写"不达线 + 缺口拆到 §4.3 的具体能力项"，不允许通过扩判据把线凑上。
6. **达标判定只在指定层做。** 线挂在哪一层由 §7 拍板后唯一指定；其余各层只发布趋势，不参与达标。
7. **发布任何精度数字必须同时声明评分口径是否含 LLM 维。** 本文档 §4 的全部数字（L0 14.0% / L1 20.0%·35.3% / L2 / L3）都在**模型一致性维缺位**的管道上算出（七维只有 6 个参与维，`score_profile` 不含 `llm`）。2026-10-08 起 LLM 维改为逐候选真实判定（回显码核验 + 事实层违反判定），其权重 0.15 会改变候选名次；因此 LLM-on 与 LLM-off 两轮结果**不可直接比较**，开 LLM 的轮次必须作为独立基线另发，并以 `score_profile` 字段自证参与维。

## 7. 结论与待拍板

**已成立的事实结论：**

1. 决策 3 的验收线（编码级 Top1 ≥25%、类目级 Top1 ≥50%）在**万条单名口径**下，无论 L0（14.0% / 26.1%）还是 L1（20.0% / 35.3%）都**不达标**，且不是口径问题——L1 已经把"不该由名字推出"和"词表没这个词"两类都摘出去了。
2. 缺口是可定位的：L1 的 5409 名未命中里，61.9% 是**有推荐但选错码**，且集中在 C/S/R/I 四章（合计 2567 名），对应 WP-B4-2 已列的三项未实现能力（肿瘤另见改道、部位扩展码、症状通道）。
3. 90 例精标语料（L3）达标但**不能单独作为验收依据**：它样本小、由人工挑选、且 7 例预期码不在词典被剔除；它能防退化，不能证明万条口径的能力。

**待拍板（验收线归属），三选一：**

| 选项 | 含义 | 代价 |
|---|---|---|
| **A｜线挂 L1，L0 只做趋势**（建议） | 25%/50% 变成"算法在可判定范围内的达标线"，本轮 20.0%/35.3%，缺口 339 名 Top1 命中，须靠 B4-2 三项能力补齐 | 需先做完 B4-2 才能宣布 B3 验收；对上汇报必须同时看到 L0 的 14.0% |
| **B｜线挂 L0（维持决策 3 原文的"万条回归"）** | 把 14.0%/26.1% 直接当达标判定 | 意味着要在单名口径上再翻 1.8 倍，实际含大量 E1/E3 类不可判定名，**近乎不可能达标**，会把验收拖成无限期 |
| **C｜线迁到新建的 L5 真实病案口径** | 用带上下文的多诊断病案做分母：源库 `WaterCloudNetDb_TongLiao.dbo.BingRenZhenDuanXinXi`（417324 行诊断、7597 个不同名、23 行缺码，含院内 ICD-10 码与 ICD-9 术式码 `D_ICD_ICD_S`，可按 `BingAH/ZhuYCSh` 组成整病例） | 最贴近上线效果，也能顺带补上手术通道口径与性别/年龄事实（WP-B3-5 医保规则的前置）；**成本是新建语料与导入链路，约 3–5 天** |

建议：**A 为主（算法层达标线）+ 立即立项 C 的 L5 语料建设**（它同时解锁手术口径与医保规则的前置缺口）。L4 人工抽查 20 例（WP-B1-3 / M5）无论选哪个都要先闭环，否则两层自动口径都缺人工校准。
