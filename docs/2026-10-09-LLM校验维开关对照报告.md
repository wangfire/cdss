## 4. 方向性归因：这 1215 次换位是变好还是变坏

把每个换码输入按"改前/改后 Top1 是否命中对照源编码"分桶（`logs/direction.mjs` → `logs/direction.json`）：

**编码级**

| 桶 | 全部输入 | 仅 L1 范围内 |
| --- | --- | --- |
| 命中→脱靶（转差） | **87** | 85 |
| 脱靶→命中（转好） | **82** | 80 |
| 两侧都不命中（换位） | 944 | 745 |
| 两侧都命中 | 0 | 0 |

净 **−5**，与 L0 的 1395→1390 完全对上（L1 口径按名称去重，故 −6）。**没有一条是"多条对照码任取其一"式的假命中**（bothHit=0）。

**类目级**（前 3 位类目相同即算命中）

| 桶 | 全部输入 | 仅 L1 范围内 |
| --- | --- | --- |
| 命中→脱靶 | 46 | 42 |
| 脱靶→命中 | **67** | 65 |
| 两侧都命中 | 283 | 260 |
| 两侧都不命中 | 717 | 543 |

净 **+21**，与 L0 类目 Top1 的 +20 对上。

**解读**：LLM 维的扰动主要表现为"同一类目内换了更细/更粗的一档"——类目层得到、编码层失去。典型转差样本：`憋气、意识丧失原因待查` R40.201→R40.200X002、`右输卵管慢性炎并积水` N70.101→N70.103、`双膝关节退行性关节病` M17.900→M17.900X002，都是**近似后缀兄弟码**被 LLM 分数抬上来。

## 5. `llm_score` 分布与那条必须说的限制

| llm_score | 条数 |
| --- | --- |
| 0.6000 | 5556 |
| 0.4000 | **10634**（众数） |
| 0.2000 | 1175 |
| 0.0000 | 24 |
| **1.0000** | **0** |

`LlmConsistencyScorer.Compute = 0.40·证据引用有效 + 0.20·候选在召回集内 + 0.20·解释被证据支撑 + 0.20·无否定/时序违规`。

**满分 0 条、上限卡在 0.60** 是万条规模的实测复现，与此前单例探针一致：0.5B 模型无法把 `cited_evidence` 落到真实证据编号上（数组恒返回 `[]`；给标量索引则输出常数；给"填 0"出口则恒 0）。因此 **0.40 权重的证据引用子维在当前模型上实际拿不到分**，LLM 维的有效取值域被压到 [0.2, 0.6]。

这意味着：LLM 维不是"接近常数的无害加数"——它有 ~0.4 的跨度，足以在兄弟码之间翻转 16% 的 Top1，但翻转方向与真值无关（净 −5）。**换模型之前，这一维只能贡献可解释性留痕，不能贡献精度。**

按治理规则 7：任何精度数字都必须声明 LLM 维是否参与；LLM-on 与 LLM-off 不可混比。本报告两组数字均已随 `score_profile` 归档。

## 7. 运营注意（本次跑批踩到的真实缺陷）

同机 CPU 推理必须显式设线程配额。ONNX Runtime 默认按**逻辑处理器数**（本机 32）开线程，与同机 Ollama 推理抢核，并发跑批时单请求中位耗时从 ~1.8s 恶化到 **9947ms**。修复：`EmbeddingOptions.IntraOpThreads` / `RerankOptions.IntraOpThreads` 默认 **4**，`OnnxEmbeddingProvider.CreateSessionOptions` 同时设 `IntraOpNumThreads`/`InterOpNumThreads`。修复后中位 **2932ms**；并发扫描 3/6/10 → 每输入 2.83 / **1.17** / 1.05 秒，取并发 6。

长跑监控教训：驱动进程静默死亡（未捕获的 AbortError）导致 12 小时无进展无人知晓。现起 `rerun_batch.mjs` 具备：单请求 try/catch + 300s 超时、500/429/超时自动重试、`unhandledRejection`/`uncaughtException` 落 `logs/batch_failures.txt`、结束时**无论成败**追加 `EXITED code=` 标记，监视端匹配 `^(DONE|EXITED)`；并按已完成 id 支持断点续跑。
