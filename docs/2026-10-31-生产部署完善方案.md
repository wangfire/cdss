## 一、现状审计（基于当前仓库实测）

| # | 审计项 | 实测结果 | 影响 |
|---|---|---|---|
| 1 | **compose 是开发口径** | api/worker 服务已在编排内（镜像构建、健康依赖齐全），但 `ASPNETCORE_ENVIRONMENT=Development`、无资源限制、无重启策略、无日志轮转；ES `xpack.security.enabled=false`、Redis 无口令、RabbitMQ 用 guest | 直接当生产用 = 明文口令 + 无认证内网服务 |
| 2 | **前端 API 地址硬编码** | `constants/common.ts` `BASE_URL: 'http://localhost:5080'` 写死；vite 无多环境构建；无 nginx 静态托管与 SPA 回退配置 | 内网部署后前端连不到后端 |
| 3 | **无生产配置文件** | 无 appsettings.Production.json；JwtAuth Key 只能靠环境变量（占位符拒绝启动已有代码强制，但无模板指引） | 每次部署靠口头约定 |
| 4 | **无 HTTPS/反代** | 无 nginx 配置；限流虽手动读 X-Forwarded-For，但无 `UseForwardedHeaders`（KnownProxies 未配置，伪造头可绕过限流分区）；无 HSTS | 安全与限流失效 |
| 5 | **DataProtection 未持久化** | 未配置 PersistKeysToXxx——容器重建后密钥环丢失，已签发的认证 Cookie/令牌类数据失效 | 重启即全员掉线 |
| 6 | 密钥管理无载体 | .env.example 只有 4 个变量；JwtAuth Key、ES 口令等无统一登记；无 secrets 模板 | 配置漂移 |

## 二、完善方案（四个工作包，一次性落地约 3~4 天）

### WP-A｜生产级部署编排（deploy/ 全套）

1. **`deploy/docker-compose.prod.yml`**（独立于 dev）：
   - api / worker / sqlserver / redis / rabbitmq / elasticsearch / **nginx** 七服务；
   - 全部 `restart: unless-stopped`；api/worker 加资源限制（mem_limit 2g/1.5g）与日志轮转（json-file max-size 10m × 3）；
   - `ASPNETCORE_ENVIRONMENT=Production`；数据卷独立命名（prod_ 前缀）；
   - ES 开 `xpack.security.enabled=true` + 证书/口令（或内网明确豁免记录）；Redis `requirepass`；
   - **healthcheck 全覆盖**（api 用 /health/ready，worker 用进程探针）。
2. **`deploy/nginx/cdss.conf`**：80→443 跳转；TLS 终结（证书路径占位）；`/api/` 反代 api:8080（含 X-Forwarded-For/Proto 透传、client_max_body_size 50m 医疗文书上传）；`/` 静态前端 dist + SPA try_files 回退；静态资源 gzip/缓存头。
3. **`src/HospitalAi.Api/Dockerfile` 适配**：确认 Production 环境变量、非 root 运行、EXPOSE 8080。
4. **`deploy/deploy.ps1`**：一键部署脚本（拉最新代码 → 检查 .env → compose up -d → 等 healthy → 冒烟探针）。

### WP-B｜前端内网部署

1. **API 地址环境变量化**：`BASE_URL = import.meta.env.VITE_API_BASE_URL ?? (同源相对路径 '/api')`——生产由 nginx 同源反代，前端不再跨域（CORS 策略随之可关）；
2. **vite 多环境**：`.env.development`（localhost:5080）/ `.env.production`（'/api'），构建产物 `dist/`；
3. **Dockerfile.admin**（node 构建 → nginx:alpine 托管 dist），并入 compose 编排；
4. **登录页医院 ID 优化**（可选）：`GET /hospitals` 下拉选择（端点已有），减少手工粘贴 GUID；
5. **验收**：内网机器浏览器访问 `https://<域名>` 完成登录→录入→推荐全流程。

### WP-C｜HTTPS / 反向代理 / 转发头

1. **代码侧**：`Program.cs` 加 `UseForwardedHeaders`（XForwardedFor | XForwardedProto，KnownProxies 配置化注入 `ForwardedHeaders:KnownProxies`）+ `UseHsts`（Production）；限流 GetClientKey 保留 X-Forwarded-For 读取（与中间件协同）；
2. **证书**：`deploy/nginx/certs/`（.gitignore，部署时放入院内签发或自签证书），文档写明 openssl 自签与院内 CA 两种路径；
3. **CORS 收口**：同源反代后生产 CORS 仅留同源（compose env 可配 origins 列表）；
4. **验收**：`https://<域名>` 全链路 200；伪造 X-Forwarded-For 被忽略（限流按真实 IP 分区）；HTTP 自动 301。

### WP-D｜密钥管理

1. **`deploy/secrets.env.template`**：全量密钥模板（JwtAuth:Key / SQL sa / RabbitMQ / ES elastic / Redis requirepass / DataProtection 盐），值不入 git；`.env` 加载到 compose；
2. **`appsettings.Production.json.template`**：非密钥生产配置模板（日志级别、限流阈值、CORS 源、ForwardedHeaders KnownProxies）；
3. **DataProtection 持久化**：api 容器挂 `prod_dpkeys` 卷 + `PersistKeysToFileSystem(/var/dpkeys)` + SetApplicationName（容器重建不掉线）；
4. **JwtAuth Key 生成指引**：文档提供 `openssl rand -base64 48` 一键生成 ≥32 字节强密钥；
5. **验收**：`git status` 无任何密钥文件；从空机器按文档走一遍部署全部成功；重启 api 容器后已登录用户不掉线。

## 四、拍板问题

| # | 问题 | 建议 |
|---|---|---|
| Q1 | 前端部署形态 | 建议 **nginx 同源反代**（消灭 CORS 与跨域 Cookie 问题），不用独立域名双前端 |

| Q4 | DataProtection 密钥是否上 DPAPI-NG/外部 KMS | 本期内网文件卷足够；上 KMS 属后续专项 |
| Q5 | 是否需要蓝绿/回滚脚本 | 本期 `deploy.ps1` 带「上一版本镜像 tag 回退」即可，不做完整蓝绿 |
