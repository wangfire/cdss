# 规则库分诊报告：890 条待确认医保规则（WP-B3-5 第一阶段）

> 日期：2026-10-07 ｜ 状态：分诊完成，执行器实现待排期 ｜ 数据源：`data/knowledge/reports/unsupported-rules.csv`（深圳医保规则库构建期无法被单条件规则模型表达的规则）
> 结构化产物：`docs/superpowers/reports/rule-triage-20261007.json`（890 条逐条归族）

---

## 1. 结论摘要

1. 890 条规则全部为**任务级审计规则**（校验"一份病案内多个编码之间的共现/属性关系"），**不适用现有单候选规则引擎**——这不是数据质量问题，而是引擎能力边界。
2. 876 条（98.4%）可归入 **8 个执行器家族**，全部指向同一个实现形态：任务级质控引擎（编码完成后对全任务编码集合做共现/属性校验，产出 quality_issue）。
3. **建议承接位置：V2.2 基线 Phase 2（全病历质控）**——这 890 条规则正是质控引擎的第一批真实需求池，避免为单条件引擎做一次性扩展后废弃。
4. 前置依赖：患者**性别与年龄**尚未进入数据模型（病例录入表单/`PatientRecord` 均无此字段），性别冲突（442 条）与年龄冲突（20 条）家族的执行器以它为前提。

## 2. 家族分布与执行器需求

| 家族 | 条数 | 条件形态 | 执行器要点 |
|---|---|---|---|
| gender-conflict（性别冲突） | 442 | 全部疾病编码 X（性别限定码，如 外阴结核） | 患者性别 × 编码性别语义（标题关键词或内建映射） |
| over-coding（疾病过度编码） | 159 | 码 A ↔ 码 B（A 已含 B 语义，B 不得单独编） | 编码共现互斥（如 结核性心包炎 ↔ 心包积液） |
| procedure-mutual-exclusive（手术合并编码） | 135 | 手术 A ↔ 手术 B 互斥（不伴/伴 变体） | 编码共现互斥 |
| merge-required（疾病合并编码） | 64 | 码 A ↔ 码 B 必须合并（星剑号联合码成对） | 编码共现合并校验 |
| missing-required（缺编码） | 48 | 码 A 存在 ⇒ 码 Z37/Z38 必须存在 | 必填伴随编码缺失校验 |
| age-conflict（年龄冲突） | 20 | 全部疾病编码 X（年龄语义码，如 老年性白内障 H25） | 患者年龄 × 编码年龄语义 |
| main-selection（主要选择错误） | 7 | 主诊断范围 × 主手术范围交叉 | 主要诊断/主要手术选择校验 |
| code-range-conflict（编码错误） | 1 | M800-M998 范围冲突 | 编码范围校验 |
| 未归档 | 14 | 条件形态特殊 | 人工逐条归档 |

## 3. 执行器统一设计草案（Phase 2 质控引擎输入）

```
RuleAuditRecord {
  RuleCode, Family, Severity
  Conditions[] = { Scope: 全部|主要, Domain: 疾病|手术, Codes[]|Range }
  Relation: GenderConflict | AgeConflict | OverCoding | MergeRequired | MutualExclusive | MissingRequired
}
```

- 上下文新增：患者性别、年龄（数据模型 + 病例录入表单同步补齐）；
- 规则来源：本报告 JSON 逐条转 `RuleAuditRecord`，导入 `coding_rule`（新 RuleType 审计类）。
