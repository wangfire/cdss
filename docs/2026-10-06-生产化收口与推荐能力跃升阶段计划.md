### WP-B3-3 LLM 实接（解释与一致性校验）

- `ModelGatewayOptions` 从 `unavailable` 切换 `openai_compatible`，接真实推理服务（医院内私有化部署或远程网关；无 GPU 开发机用 CPU 小模型/远程 API 先跑通）；
- 现有"解释 + supported JSON Schema 校验、2 次重试"逻辑（`V22LiteCodingPipelineRunner.cs:911-971`）实跑，Prompt 版本化进 `V22PipelineOptions`；
- 失败语义：校验不通过 → 降置信/转 `NEED_REVIEW`，不伪造 `ACCEPT`。

> 进展（2026-10-08 收口）：本地 CPU 推理已实接（Ollama `qwen2.5:0.5b-instruct`，`model.small` 映射），解释调用改为**逐候选**（每输入至多 3 个候选、每候选至多 5 条证据原文）；Prompt 补入诊断原文、候选编码、带编号的证据原文与事实线索，并把原恒真的两条判据换成可核验判据——`CandidateExistsInRetrieval` 用该输入的检索池编码核验模型回显码，`NegationOrTemporalViolation` 由结构化事实（否定/排除/既往/家族）叠加模型自报得出，事实层只能加重、不可被模型推翻；`PromptVersion` 升到 `v22-explanation-v2`。
> 实测结论（诚实口径）：证据引用维在当前 0.5B 模型上**拿不到分**——数组形式 `cited_evidence` 恒答 `[]`，改标量 `evidence_index` 则恒答固定编号（把候选名单缩短到 2 条才偶尔正确），属模型能力上限而非链路缺陷，因此校核器按"无据主张不予加分"处理，是正确行为。换更强模型前，LLM 维实际只有"回显码在池内 + supported 自报 + 无违反"三部分生效。

### 9.1 同机 CPU 推理线程配额（2026-10-09 实测）

ONNX Runtime 不显式设限时，会按**逻辑处理器数**（本机 32）开推理线程；Ollama 在同机跑 LLM 校验时双方抢核，并发跑批的单请求中位耗时从 ~1.8s 恶化到 **9947ms**。

- 修复：`EmbeddingOptions.IntraOpThreads`、`RerankOptions.IntraOpThreads` 默认 **4**；`OnnxEmbeddingProvider.CreateSessionOptions` 同时设 `IntraOpNumThreads` 与 `InterOpNumThreads`（向量与 Rerank 共用）。
- 修复后中位 **2932ms**；并发扫描 3/6/10 → 每输入 2.83 / **1.17** / 1.05 秒，万条跑批取并发 6。
- 部署含义：生产机上若 LLM 走 CPU，模型侧线程配额必须按"同机核数预算"统一配置，不能各自默认。

长跑批监控四层（缺一层就会静默停摆）：

1. **进程内不致死**：单请求 try/catch + 300s 超时、500/429/超时自动重试、`unhandledRejection`/`uncaughtException` 落 `logs/batch_failures.txt`（`logs/rerun_batch.mjs`）。
2. **幂等续跑**：明细 append-only jsonl，按已完成 id 过滤，杀掉重启不重复。
3. **终态标记**：启动命令无论成败都追加 `EXITED code=`，监视端匹配 `^(DONE|EXITED)` 而非只匹配 `DONE`——本轮曾因未捕获 AbortError 静默死亡，12 小时无进展无人察觉。
4. **心跳 + 独立看门狗**：每完成一条原子写 `logs/batch_heartbeat.json`（`{pid,done,total,failed,etaMin,updatedAt}`）；`logs/watch_batch.mjs` 单次检查，心跳超阈值**或从未写出**即输出 `STALLED` 并 exit 2。判据必须是"证据消失"，不是"成功标志出现"；看门狗还要跑在与工作进程不同的时钟上（定时任务每 15 分钟调用一次），否则进程死了监视一起死。
